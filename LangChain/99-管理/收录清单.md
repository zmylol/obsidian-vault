2026-10-14 · 已完成 · [原文](https://www.langchain.com/blog/context-engineering-deep-agents-remember)

Deep Agents 把长任务的上下文管理放进 Agent 运行框架：大工具结果与长用户消息先落到文件，模型只看预览；对话接近窗口上限时压缩旧消息，但保留可读回的原始记录。Skills 按需加载完整指令，子 Agent 在独立上下文中处理噪声工作，长期记忆则以文件跨会话保存。原文给出的约 2 万 token 工具结果、5 万 token 用户消息和 85% 摘要触发点是当前默认示例，可配置；文章解释机制，没有提供这些做法对准确率的受控比较。

### [用 ScaleDown 为长运行 Agent 压缩上下文](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2026-10-13%20-%20%E7%94%A8%20ScaleDown%20%E4%B8%BA%E9%95%BF%E8%BF%90%E8%A1%8C%20Agent%20%E5%8E%8B%E7%BC%A9%E4%B8%8A%E4%B8%8B%E6%96%87.md)

2026-10-13 · 已完成 · [原文](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents)

ScaleDown 为 LangChain 与 Deep Agents 提供受限解码模型和三类中间件，把长任务中的狭窄上下文决策交给专用模型：Summarize 压缩旧历史、Compress 按查询裁剪工具结果、Extract 从用户消息复制字段并可分类。文章称模型最多接受 100 万 token；ScaleDown 自有公开数据集基准称，相对 GPT-5.5、GPT-5.4 Mini 和 Nano 的平均值，Summarize 便宜 41 倍、快 2.7 倍，Compress 便宜 138 倍、快 1.8 倍。摘要失败时原历史保留，但真实 Agent 的准确率、重取行为和端到端收益仍需验证。

**要点：** Summarize、Compress 与 Extract 分别处理历史、工具结果和结构化字段。

### [在多 Agent Harness 中组织共享与隔离上下文](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2026-09-08%20-%20%E5%9C%A8%E5%A4%9A%20Agent%20Harness%20%E4%B8%AD%E7%BB%84%E7%BB%87%E5%85%B1%E4%BA%AB%E4%B8%8E%E9%9A%94%E7%A6%BB%E4%B8%8A%E4%B8%8B%E6%96%87.md)

2026-09-08 · 已完成 · [原文](https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness)

Deep Agents 为子 Agent 提供两种上下文模式：默认 isolated 只接收任务描述，fork 则继承主 Agent 的状态和对话，完成后都只把结果交回主流程。作者建议让接续实现的执行者继承已收集的资料，让独立审查者从任务与待审材料出发，减少受到先前判断的影响。继承上下文可复用提示缓存并减少重复读取，但也会带入更长历史；文章没有给出跨任务的统一速度或成本提升。这里调整的是信息传递方式，访问权限仍需另行配置。

**要点：** isolated 模式不继承前面的诊断过程，适合 reviewer 或能独立描述的研究问题，减少被监督 Agent 的判断引导。它也可能重复收集已有资料；上下文隔离本身不等于权限或隐私隔离。

### [让 OpenWiki 记忆根据证据自我纠错](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2026-08-25%20-%20%E8%AE%A9%20OpenWiki%20%E8%AE%B0%E5%BF%86%E6%A0%B9%E6%8D%AE%E8%AF%81%E6%8D%AE%E8%87%AA%E6%88%91%E7%BA%A0%E9%94%99.md)

2026-08-25 · 统计口径待核实 · [原文](https://www.langchain.com/blog/self-correcting-memory-openwiki)

OpenWiki 0.4.0 为知识库中的事实记录代码依据及其版本，来源变化时先标记待核验，再在后续更新中刷新证据或同时修正文档，让未解决的不确定性持续保留。团队用同一仓库的提交序列比较启用与未启用这套机制的结果，表格中获代码支持的事实比例从 92.9% 升至 97.8%，两组各标注 2,000 条事实。它展示了逐步纠错的可能性，但正文过时事实计数与表格比例不一致，统计口径仍待核实，不能据此推算统一改善幅度或外推到其他领域。

**要点：** 运行时在更新开始前确定性地比较证据版本，无需模型遍历判断。版本不同只说明不能继续默认相信；无需另存 stale 标志，旧证据版本会让未解决的不确定性持续存在。

### [用 OpenWiki Brains 把多源信息维护成 Agent 记忆](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2026-07-10%20-%20%E7%94%A8%20OpenWiki%20Brains%20%E6%8A%8A%E5%A4%9A%E6%BA%90%E4%BF%A1%E6%81%AF%E7%BB%B4%E6%8A%A4%E6%88%90%20Agent%20%E8%AE%B0%E5%BF%86.md)

2026-07-10 · 已完成 · [原文](https://www.langchain.com/blog/introducing-openwiki-brains-general-purpose-wiki-memory-for-agents)

OpenWiki 0.1.0 把原有的代码仓库文档能力扩展为通用记忆：Personal Brain 根据用户关注范围，从已连接的信息源提取内容，写成本地 Markdown 知识库并按计划刷新。邮件和代码提交等来源可按固定方式拉取，Notion 与网页搜索则由 Agent 带着目标检索；Code Brain 仍单独负责仓库知识。发布时首批连接器包括 Gmail、Notion、Git、X、Hacker News 和网页搜索，Slack 及更完善的检索仍是后续计划，不能把路线图当作已有功能。

**要点：** Personal Brain 依据用户关注范围选择信息；它可主动从已连接来源取材，不必等待每次对话显式要求记住。

### [上下文工程的四种基本操作](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2025-07-02%20-%20%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B%E7%9A%84%E5%9B%9B%E7%A7%8D%E5%9F%BA%E6%9C%AC%E6%93%8D%E4%BD%9C.md)

2025-07-02 · 已完成 · [原文](https://www.langchain.com/blog/context-engineering-for-agents)

LangChain 将长任务中的上下文管理归纳为四种操作：把资料写到窗口外、按任务选回所需内容、压缩历史与工具结果，以及用子 Agent 或运行状态隔离中间信息。文章结合产品与论文案例说明，这些方法可减少无关信息，但记忆可能选错、摘要可能漏掉关键决定，多 Agent 也会增加协调和令牌成本。作者建议先观察真实调用与用量，再用任务评估检验改动。它提供设计方法和案例综述，没有对四种策略做统一实验，效果需按具体任务验证。

**要点：** 模型调用与工具调用交替运行，搜索结果和历史记录不断增长。问题包括容量、成本，以及错误或冲突信息对后续判断的影响。

### [把上下文工程理解为动态信息系统](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AE%A1%E7%90%86/2025-06-23%20-%20%E6%8A%8A%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B%E7%90%86%E8%A7%A3%E4%B8%BA%E5%8A%A8%E6%80%81%E4%BF%A1%E6%81%AF%E7%B3%BB%E7%BB%9F.md)

2025-06-23 · 已完成 · [原文](https://www.langchain.com/blog/the-rise-of-context-engineering)

Harrison Chase 将上下文工程定义为动态组织信息、工具和表达格式的系统：每次调用都要按任务需要，从用户输入、历史记录、检索及工具结果等来源准备材料。提示词写作是其中一部分，缺少关键资料或传入难以理解的数据，需要从整个信息流程中修正。文章建议用 LangGraph 控制处理步骤和模型输入，再用 LangSmith 查看实际调用，区分上下文不足与模型能力不足。作者认为许多 Agent 错误源于信息传递，这属于工程判断，文中没有量化实验来证明其适用于所有任务。

**要点：** 上下文来自用户、开发者、历史交互和外部工具，组装逻辑因此需要随任务状态变化。

### [让 Deep Agents 的 Skills 按需加载工具与指令](../01-文章/工程与Agent/运行架构/2026-10-07%20-%20让%20Deep%20Agents%20的%20Skills%20按需加载工具与指令.md)

LangChain 为 Deep Agents 的 Skills 增加三组能力：工具可绑定到技能并在读取技能后才披露，用户显式点名的技能可在首次模型调用前预加载，长线程也能重新扫描技能库。文章以渐进式披露解释设计：系统提示只放名称和描述，完整 SKILL.md 及脚本、参考和资源按任务逐级读取，从而控制上下文增长。工具绑定还可按运行时权限返回工具，但技能重载会改变系统提示并可能使提示缓存失效；这些是产品机制说明，文中没有给出统一延迟或质量实验。

### [在 Agent 运行框架内按任务路由模型](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%BF%90%E8%A1%8C%E6%9E%B6%E6%9E%84/2026-10-01%20-%20%E5%9C%A8%20Agent%20%E8%BF%90%E8%A1%8C%E6%A1%86%E6%9E%B6%E5%86%85%E6%8C%89%E4%BB%BB%E5%8A%A1%E8%B7%AF%E7%94%B1%E6%A8%A1%E5%9E%8B.md)

2026-10-01 · 已完成 · [原文](https://www.langchain.com/blog/how-to-build-a-model-router-in-the-harness)

LangChain 为 Open SWE 编码 Agent 在运行框架内加入三档模型路由，按每个会话首条请求选定模型，并沿用至会话结束。在973个会话的内部 A/B 测试中，相比始终使用 GPT-6 Astra，每会话 LLM 成本中位数由2.61美元降至0.94美元，约降64%；合并 PR 的会话占比为29.2%对27.3%（p=0.49），未检出显著差异，不能据此证明质量等同。方案仍是概念验证，尚未覆盖会话中途换模型和对子 Agent 的统一路由。另一次以始终使用快速模型为对照的 A/B 试验因工程师反馈输出质量低而提前终止，未形成有统计意义的结果。

**要点：** 路由条件依赖具体任务，当前每会话只选一次模型；成本下降与PR结果指标应分别核验，不能以未检出差异宣称质量等同。

### [用 Jev 为 Agent 分担结构化决策](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%BF%90%E8%A1%8C%E6%9E%B6%E6%9E%84/2026-09-17%20-%20%E7%94%A8%20Jev%20%E4%B8%BA%20Agent%20%E5%88%86%E6%8B%85%E7%BB%93%E6%9E%84%E5%8C%96%E5%86%B3%E7%AD%96.md)

2026-09-17 · 已完成 · [原文](https://www.langchain.com/blog/building-a-harness-with-jev)

Jev 是一种不生成文本、只返回结构化判断与概率的决策模型，可让 Agent 把部分分类任务从完整的语言模型调用中分离出来。LangChain 通过 TypeSafeClassifier 接收上下文和问题，支持选项分类、有序评分及是非判断，并提供实验性的模型路由和工具执行前风险检查中间件。它适合辅助决定调用哪个模型、是否阻止某次工具操作，开放式推理和生成仍由语言模型承担。提速降本来自供应商针对分类任务的报告，文中没有独立基准，也未证明这种检查能保证工具操作安全。

**要点：** 结构化分类辅助模型路由和工具调用前检查；生成任务仍交给语言模型，性能与安全效果需要在实际流程验证。

### [用 Deep Life Sci 组合科研检索、沙箱与评估](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%BF%90%E8%A1%8C%E6%9E%B6%E6%9E%84/2026-09-17%20-%20%E7%94%A8%20Deep%20Life%20Sci%20%E7%BB%84%E5%90%88%E7%A7%91%E7%A0%94%E6%A3%80%E7%B4%A2%E3%80%81%E6%B2%99%E7%AE%B1%E4%B8%8E%E8%AF%84%E4%BC%B0.md)

LangChain 把合成 Agent 评估的构建分成两步：先用自然语言明确任务，再据此生成可运行的 Harbor 测试。跨任务共用的接口、数据结构和生成方法写入“世界规格”，单个任务的输入、环境和评分条件写入任务规格，便于人工审阅后批量生成。团队先试做少量任务，再观察实际运行轨迹和不同模型的表现，修正环境漏洞并校准难度。这是一套迭代工作方法，没有定量效果对照；领域真实性与任务难度仍需要人的判断。

**要点：** world spec 可保存服务 schema、mock 方法、数据生成脚本与评分规范；task spec 则明确本次环境、输入和评分条件。Markdown 规格便于人工讨论，避免直接审查大批生成代码。

### [用 Tuned Evaluators 持续评估 Agent 的感知错误](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%AF%84%E4%BC%B0%E4%B8%8E%E5%8F%AF%E9%9D%A0%E6%80%A7/2026-08-18%20-%20%E7%94%A8%20Tuned%20Evaluators%20%E6%8C%81%E7%BB%AD%E8%AF%84%E4%BC%B0%20Agent%20%E7%9A%84%E6%84%9F%E7%9F%A5%E9%94%99%E8%AF%AF.md)

LangChain 发布 Tuned Evaluators，由平台维护面向特定目标的评估器，判断与解释直接附在调用记录上。首款 Perceived Error 用专门后训练的模型，从用户纠正、反复请求等线索识别疑似错误；公司内部基准报告其判别效果优于所测前沿模型且成本更低，但它仍是待调查信号。2026 年 8 月发布时，该款仅面向美国区 Plus 和 Cloud Enterprise。对话至少包含两组人机消息并达到设定的空闲时间后才符合条件，评估在此后 12 小时内完成。

**要点：** 平台负责提示、模型和版本；结果附解释回到调用记录，供定位失败、人工复查和补充评估样例使用。

### [用 IssueBench 评估 Agent 问题发现引擎](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%AF%84%E4%BC%B0%E4%B8%8E%E5%8F%AF%E9%9D%A0%E6%80%A7/2026-07-20%20-%20%E7%94%A8%20IssueBench%20%E8%AF%84%E4%BC%B0%20Agent%20%E9%97%AE%E9%A2%98%E5%8F%91%E7%8E%B0%E5%BC%95%E6%93%8E.md)

2026-07-20 · 已完成 · [原文](https://www.langchain.com/blog/issuebench-how-we-evaluate-engine)

IssueBench 是 LangChain 用来检验问题发现引擎 Engine 的内部基准：它让系统把调用记录转成便于工程团队处理的问题卡片。现有 15 个合成任务覆盖运维、软件开发和客服，混入干净记录与 15 类已知故障，同时检查故障识别、分类、已有问题归属和新问题聚类。即使找对故障，重复建卡、乱合并或覆盖已有上下文也会扣分。这套设计提供了可重复的回归检查方法，但文章没有给出性能排名，合成任务也不能代表所有生产场景。

**要点：** 每个任务提供已知问题卡片及混合调用记录；系统既要辨认故障，也要决定与已有卡片的关系。

### [评估 Agent 时检查决策、产物与最终状态](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%AF%84%E4%BC%B0%E4%B8%8E%E5%8F%AF%E9%9D%A0%E6%80%A7/2025-12-03%20-%20%E8%AF%84%E4%BC%B0%20Agent%20%E6%97%B6%E6%A3%80%E6%9F%A5%E5%86%B3%E7%AD%96%E3%80%81%E4%BA%A7%E7%89%A9%E4%B8%8E%E6%9C%80%E7%BB%88%E7%8A%B6%E6%80%81.md)

2025-12-03 · 已完成 · [原文](https://www.langchain.com/blog/evaluating-deep-agents-our-learnings)

LangChain 从四款 Deep Agents 应用的开发中总结：评估应为每个任务分别规定成功条件，按需检查工具决策、最终回复或实际生成的文件等状态。单步测试用于检查下一次动作，完整运行验证最终结果，多轮测试则在每轮确认预期后继续，偏离时及时失败，避免后续输入失去意义。每个用例还应重置环境，并可回放外部请求以减少不稳定因素。这是团队的测试设计经验，没有统一效果对照；单步判断正确不能替代完整任务验收。

**要点：** 单步测试适合检查下一次工具选择；完整执行检查任务结果；多轮测试还要确认前一轮结果足以支持后续输入。

### [用 Connections 为 Managed Deep Agents 分配凭据与调用者身份](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E9%83%A8%E7%BD%B2%E4%B8%8E%E6%8C%81%E4%B9%85%E5%8C%96/2026-09-09%20-%20%E7%94%A8%20Connections%20%E4%B8%BA%20Managed%20Deep%20Agents%20%E5%88%86%E9%85%8D%E5%87%AD%E6%8D%AE%E4%B8%8E%E8%B0%83%E7%94%A8%E8%80%85%E8%BA%AB%E4%BB%BD.md)

2026-09-09 · 已完成 · [原文](https://www.langchain.com/blog/connections-managed-credentials-and-per-caller-identity-for-managed-deep-agents)

Managed Deep Agents 的 Connections 把凭据集中保存在 LangSmith 工作区，工具运行时可读取部署共享的凭据，或按实际调用者解析个人授权。这样，同一部署能根据各人的访问权查询资源，并以请求者身份创建问题，而不必让所有操作都使用同一服务账号。缺少用户授权或令牌过期时，运行会暂停并请求授权；共享密钥轮换也不必把新值打进代码包。发布时功能仍属预发布版，凭据归属在创建时确定，部署共享连接须先有部署。

**要点：** Agent-owned 或 user-owned 决定使用谁的身份；secret 或 OAuth 决定凭据形式。归属在创建时确定，connections.get() 不会临时改变所有权。共享搜索 key 的轮换可以独立于部署代码。

LangSmith Preview Builds 为代码合并请求的源分支创建临时部署，让同事在同一运行环境里检查提示、工具和模型改动；追加提交会自动生成新版本，父部署不受这次代码更新影响。团队可按每个请求或指定标签触发，用闲置时限自动回收，并以并发上限控制同时运行的数量。预览创建时会复制父部署的凭据，因此运行环境独立不等于权限独立。2026 年 8 月发布时，该功能为公开测试版，仅面向 LangSmith Cloud 中通过 GitHub 集成连接的部署。

**要点：** 预览与父部署关联但运行源分支，不更新父部署。评审者可验证工具行为、失败路径和 traces；多个 PR 有各自环境，减少共用 staging 来回切分支。

LangChain 的 Kubernetes 运维 Agent 把例行巡检与深入调查分开：前者先用 Python 收集集群状态，再由小模型生成报告；后者才启动协调者和多个专职子 Agent。作者报告，这使内部每次巡检成本降低 95%–99%，但该数字不代表所有运维任务。系统能自主读取集群，所有写操作仍须人工批准，并由工具隔离和集群权限共同限制。调用追踪和审批反馈用于形成回归测试，发现问题后再验证修复效果。

**要点：** 定时任务用 Kubernetes 客户端采样，再进行一次 Haiku 调用；深入调查才交给 Sonnet 协调者和只读专家。

### [为什么 Agent 需要可隔离、可持久化的计算环境](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E9%83%A8%E7%BD%B2%E4%B8%8E%E6%8C%81%E4%B9%85%E5%8C%96/2026-07-15%20-%20%E4%B8%BA%E4%BB%80%E4%B9%88%20Agent%20%E9%9C%80%E8%A6%81%E5%8F%AF%E9%9A%94%E7%A6%BB%E3%80%81%E5%8F%AF%E6%8C%81%E4%B9%85%E5%8C%96%E7%9A%84%E8%AE%A1%E7%AE%97%E7%8E%AF%E5%A2%83.md)

2026-07-15 · 已完成 · [原文](https://www.langchain.com/blog/agents-need-their-own-computer)

需要运行代码、安装依赖和反复检查结果的 Agent，还需要文件系统、计算资源和可延续的工作状态。LangChain 提出用独立内核的微型虚拟机承载这些操作，再配合凭据代理、资源限制和快照分支，形成可隔离、可观察的执行环境。文章同时强调，沙箱只能限制执行影响，不能消除外部内容对模型的提示注入；只调用固定接口、不运行动态代码的 Agent，也未必需要托管沙箱。文中介绍的是产品架构，未报告独立效果评测。

**要点：** 动态代码在隔离环境运行，同时设置凭据代理、资源上限和操作记录；模型提示本身不是执行边界。

2026 年 4 月推出测试版的 Deep Agents Deploy，把模型、核心指令、Skills、MCP 工具和可选沙箱配置打包到 LangSmith Deployment 服务，并提供交互、人工介入及记忆访问接口。其设计把执行框架、运行服务和会话环境放进一次部署流程，同时用文件格式与 API 保留记忆的访问路径；选择自托管时，记忆可留在自己的数据库中。文章强调模型与基础设施选择权，相关竞品比较属于发布方立场，没有独立性能评测；开源框架也不代表托管服务免费或无需部署条件。
