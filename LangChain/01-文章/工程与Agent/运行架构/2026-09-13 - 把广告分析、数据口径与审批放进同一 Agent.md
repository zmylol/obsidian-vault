# 把广告分析、数据口径与审批放进同一 Agent

<!-- AUTO:BEGIN -->
[← 首页](../../../00-首页.md) · [本分类文章](../../../99-管理/收录清单.md#%E8%BF%90%E8%A1%8C%E6%9E%B6%E6%9E%84)

## 摘要

LangChain 把广告周报和 Slack 问答合并为同一套 Agent，让不同入口按需取得工具，并由各平台子 Agent 分担分析。系统把可复用的方法、公司知识和实时数据分开保存，用代码计算指标、规定数据来源，再让模型解释结果和提出调整。团队在早期报表流程的内部对照中报告，运行时间从约 18 分钟缩至 85 秒、费用降至约原来的 1/40；这些结果只对应其内部流程。投放变更仍需授权人员审批，再由代码执行并核对平台结果，持续主动监测属于后续计划。

## 重点文字解读

### 工作环境和知识分层一起设计

团队给 Agent 配备带分析与报表软件的沙箱，把提示作为导航：Skills 保存可复用的方法，wiki 保存公司口径和决策，实时工具提供变化中的数据，确定性代码约束计算和硬规则。方法与业务知识分别维护，避免把全部材料塞进系统提示。

### 周报与问答共用运行逻辑

原先周报和 Slack 分成两个图，能力需要重复实现，问答也无法直接跟进报表。合并后按入口提供不同工具；周报由父 Agent 分派各平台子任务，每个线程保留自己的沙箱和检查点。共用的是运行定义，状态仍需隔离。

图示：两个独立图合并为同一个图定义，共享 wiki、技能、工具和来源规则；Slack 与定时运行取得不同工具集合，不表示所有请求共用同一份状态。

*两个独立图合并为同一个图定义，共享 wiki、技能、工具和来源规则；Slack 与定时运行取得不同工具集合，不表示所有请求共用同一份状态。* [原图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa74e3527f3ee081d22cefc_7ff.png) · [文章出处](https://www.langchain.com/blog/paid-media-agent)

### 先算清数字，再让模型解释

Python 负责对齐日期窗口、匹配账户及计算指标。广告平台提供花费、曝光和点击，数仓提供线索、商机与销售管线；无法可靠关联的数据保留限制。团队报告早期报表流程约便宜40倍，运行从约18分钟降至85秒，属于内部工作流对照。

### 工具目录按问题展开

广告工具通过 Search、Read、Run 三步按需取得定义，写入走独立审批路径；数仓同时保留常用固定查询和可检查表结构的分析查询。这样既能处理常见问题，也能组合回答未预先设计的问题，仍需核对查询来源与指标口径。

图示：工具目录留在服务端，Agent 先搜索、再读取所选工具结构并调用；图中的218个工具不是每次都完整放入上下文，广告写入另走审批路径。

*工具目录留在服务端，Agent 先搜索、再读取所选工具结构并调用；图中的218个工具不是每次都完整放入上下文，广告写入另走审批路径。* [原图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6aa74e48f43dc1e967f31eb4_8ff.png) · [文章出处](https://www.langchain.com/blog/paid-media-agent)

### 隔离完成状态，并把审批落在服务端

平台子 Agent 曾因共用报表路径和完成标记而相互干扰，团队为各平台分别保存文件与状态，并限定读取、计算、渲染三类工具。投放建议交给指定人员在 Slack 中修改或批准，服务端核对用户身份，再执行并查询平台确认结果。

## 适用条件与局限

正文是团队自身工程复盘，性能数字对应其早期报表流程，业务增长与获客成本变化不能据此单独归因于 Agent。持续主动监测、跨团队共享学习和更复杂的专用界面仍属后续工作。已读正文并检查8张图片，节选4张；公开代码、广告账户、演示活动与外链内容未运行或单独验证。

## 怎样理解与应用（AI 解读）

把类似方法用于知识库时，可让代码负责 URL 去重、日期窗口和文件计数，让模型负责解读；每个来源使用独立输出路径与完成状态。若以后允许 Agent 改动外部数据，应把批准内容、执行结果和回读核验分别保存，而不能凭一条“完成”回复验收。
