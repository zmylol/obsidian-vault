# 把仓库文档接入每日更新与统一检索门户

## 摘要

Credit Genie 为解决仓库文档过时、知识集中在少数人手中的问题，用 OpenWiki 在各仓库保存文档，再汇总到可搜索的 GitHub Pages 门户。夜间任务发现有效代码变化后生成文档更新请求，每日任务自动合并并重建门户，供同事查询；编码 Agent 开工前则读取仓库内的 openwiki/ 文档。团队称这让跨仓库信息更容易找到，也改善了人员熟悉系统的过程，但文章没有给出量化对照。把跨仓库依赖图接入 OpenWiki 仍是下一阶段计划，不能当作现成功能。

## 重点图文解读

### 仓库内保存，门户统一发现

文档留在每个仓库的 openwiki/ 目录，编码 Agent 被要求先读取它；人通过跨仓库可搜索门户找资料。统一入口并未移走仓库内的上下文。

### 接入与刷新形成两条流水线

向门户配置增加仓库会触发工作流接入 PR；夜间任务发现有意义的提交变化后生成文档更新 PR。每日 sweep 合并积压更新并重建门户，减少人工维护断点。

### 跨仓库依赖仍是后续目标

文中下一阶段才计划接入已有的跨仓库知识图谱，用于解释系统关系和变更影响；当前门户效果不能当作这项能力已经完成。

## 适用条件与局限

收益来自客户经验，没有给出受控实验或量化准确率。自动批准和合并依赖该团队的权限与审查策略；嵌入演示视频未逐段核验。

## 怎样理解与应用（AI 解读）

先在一个仓库记录“代码提交到文档可搜索”的延迟，再检查变更是否有来源证据和回滚入口；不要仅用生成文件数衡量文档质量。
