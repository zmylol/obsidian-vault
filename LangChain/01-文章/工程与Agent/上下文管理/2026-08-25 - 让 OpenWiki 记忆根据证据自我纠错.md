# 让 OpenWiki 记忆根据证据自我纠错

## 摘要

OpenWiki 0.4.0 为知识库中的事实记录代码依据及其版本，来源变化时先标记待核验，再在后续更新中刷新证据或同时修正文档，让未解决的不确定性持续保留。团队用同一仓库的提交序列比较启用与未启用这套机制的结果，表格中获代码支持的事实比例从 92.9% 升至 97.8%，两组各标注 2,000 条事实。它展示了逐步纠错的可能性，但正文过时事实计数与表格比例不一致，统计口径仍待核实，不能据此推算统一改善幅度或外推到其他领域。

## 重点图文解读

### stale 表示证据需复核

运行时在更新开始前确定性地比较证据版本，无需模型遍历判断。版本不同只说明不能继续默认相信；无需另存 stale 标志，旧证据版本会让未解决的不确定性持续存在。

### 修正结论与证据一起提交

Agent 阅读页面时收到其过时 claim：仍然正确则刷新证据版本，已错误则同时改正文与依据。未处理项继续留待后续；OKF v0.2 用 sources、generated、verified 暴露页面来源和核验历史，详细 claim 留在 sidecar。

### 实验结果不能掩盖口径差异

原文按一串 git commits 回放并在检查点更新 wiki。表格给出的 supported 比例为 92.9%→97.8%，stale 为 3.5%→0.5%（两组均标 n=2000）；正文另列 stale 数量 80→9。基线 3.5% 按 2000 条计算为 70，与正文的 80 不一致；启用组 9/2000=0.45%，显示为 0.5% 可能来自取整。来源未解释统计口径，不能据此推算统一的下降幅度。

## 适用条件与局限

数据来自团队的代码仓库回放，不是跨领域通用结论；原文计数与百分比口径有不一致，具体样本汇总方式待核实。本文未复现评估。

## 怎样理解与应用（AI 解读）

知识库可为关键结论保存来源版本，变更后进入待复核队列；只有实际重读和保存后才更新核验时间，避免以“抓取成功”替代“结论仍然正确”。
