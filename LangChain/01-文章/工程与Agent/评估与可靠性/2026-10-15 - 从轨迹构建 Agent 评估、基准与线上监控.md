# 从轨迹构建 Agent 评估、基准与线上监控

## 摘要

LangChain 给出一套从真实轨迹启动 Agent 评估的方法：先挑一个重要行为，收集约 10–20 个案例建立基线，再把新失败持续加入数据集。离线评估在发布前比较版本，线上评估对生产轨迹抽样监控；代码检查、模型裁判、人工审核和成对比较各有适用范围。对会改动文件或系统状态的长任务，还需在隔离环境中检查最终状态，而不只看回复。文中的案例和成本比较用于说明设计取舍，不保证任意 Agent 获得相同分数或费用。

## 重点图文解读

### 从失败轨迹建立最小数据集

先读一批真实 trace，选一个可判断的行为，例如旅行 Agent 是否按用户指定日期与预算订票。团队建议先把约 10–20 个案例做成数据集，对当前版本运行基线实验；后来在生产或试用中发现的失败再补进同一行为的数据集。图中的旅行 Agent 虽以 385 美元满足预算，却把“下周五”搜索成周六，说明只查价格会漏掉路径中的错误。

图示：原文图：旅行订票轨迹中的错误日期

*图注：示例工具调用的日期与用户要求不符，即使最终价格低于 400 美元，仍应成为新的回归案例。* [原图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6ac981161c8c62fb29de8f27_travel-booking-trace-light.png) · [文章出处](https://www.langchain.com/blog/common-questions-about-agent-evals)

### 离线、线上与评估器如何配合

离线评估在发布前对固定案例比较版本；线上评估检查真实生产轨迹，并把新问题反哺离线集。代码评估器适合预算等确定性条件，模型裁判适合回答是否有依据等开放问题，人工审核为主观质量及裁判校准提供信号，成对比较适合挑选提示词或模型。模型裁判宜问狭窄问题并使用二元或少量标签，且与人工标注核对，不宜依赖模糊的 1–10 分。

### 长任务基准检查最终环境

当 Agent 会安装包、改文件或调用服务，单看最终回复不足以证明任务完成。文章用 Harbor 说明：每个基准任务有独立容器、初始环境及测试脚本，脚本检查运行后的外部状态，结果写入 LangSmith 实验。图中的 75% 是四个示意任务通过三项的演示数，不是产品真实基准成绩。

图示：原文图：Harbor 在隔离环境中检查任务结果

*图注：左侧任务定义说明和测试脚本，中间沙箱执行，右侧把示例结果写到 LangSmith；75% 仅为图中四项示例任务的演示比率。* [原图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/6ac981161c8c62fb29de8f18_harbor-eval-flow-light.png) · [文章出处](https://www.langchain.com/blog/common-questions-about-agent-evals)

### 费用与多轮对话

线上模型裁判可只抽样或过滤负面反馈，确定性条件优先用代码检查。文章转述其 Jev 实验的特定通过/失败比较和费用，不应外推为所有评估任务。多轮对话需用 thread ID 汇聚每一轮，再评价最终预订是否反映用户中途改期等要求；单轮均看似正常仍可能全程失败。

## 适用条件与局限

10–20 个案例是作者建议的启动规模，并非覆盖率保证。模型裁判需与人工判断比对；线上抽样可能漏掉稀有失败。图示的四任务 75% 为教学示意，不能作为实际 Agent 分数；示例代码及 Harbor 任务未在本库运行。

## 怎样理解与应用（AI 解读）

**AI 解读：**可把一次线上错误同时转成“工具调用参数”和“最终环境状态”两种检查，再用固定案例比较发布前后版本。若模型裁判与人工在某类错误上常分歧，应先收窄问题及标签定义，再扩大线上抽样；这是基于原文方法提出的实施建议。
