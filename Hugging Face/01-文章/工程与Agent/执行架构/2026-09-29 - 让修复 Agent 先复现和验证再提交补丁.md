# 让修复 Agent 先复现和验证再提交补丁

<!-- AUTO:BEGIN -->
[← 首页](../../../00-首页.md) · [本分类文章](../../../99-管理/收录清单.md#执行架构)

> [原文](https://huggingface.co/blog/huggingface/anatomy-of-a-bug-fixing-agent) · Anatomy of a bug-fixing agent · 2026-09-29 · Tarek Ziadé，Hugging Face团队作者，社区入口发布。本文为项目方运行报告，未独立复现结果；关联代码未执行、链接PR未逐个审阅、论文未精读。

## 摘要

Tarek Ziadé 介绍了用于Transformers夜间CI的修复Agent Serge：先筛出持续失败的测试，在GPU复现并查找已有修复，再生成补丁，将修改前后的目标测试各运行5次，通过后提交PR供维护者审核。作者报告约80天有29项修复合并；最近两周117组失败中，86组进入实际模型会话，24次通过验证的PR事件对应19个不同PR，并非24项合并。流程不会自动提交无法安全修复或验证的候选，但仍不能自动可靠区分合理修改测试期望与钻测试空子，基础设施失败也不算补丁有效的证据。

## 重点图文解读

### 1. 把维护者反复等待GPU的过程交给流程

Transformers集成测试在真实GPU上运行模型检查点，不能在每个提交上全部执行。Serge聚焦过去一周持续失败的测试，先在新GPU运行器中多次复现；如果已经通过或不能可靠复现，就停止，不先让模型猜补丁。

随后用relore查历史讨论与进行中的修复。作者举例，GPTNeoXJapanese回归已有获批PR，Serge因此没有重复提交。本篇关注修复流程的准入与停止条件；[relore笔记](../记忆与上下文/2026-09-21%20-%20让%20Agent%20从仓库讨论追溯当前代码的决策.md)侧重历史证据如何与当前代码连接。

![Serge六步修复流程](../../../98-附件/原文配图/serge-steps.png)

*图1：六步流程先筛选、复现和查重，之后才生成、验证与提交PR；正文补充修改前后各运行5次。图中的发布PR只是进入维护者审核，不能自动合并main。 [原图](https://huggingface.co/datasets/huggingface/tarek-blog-posts-images/resolve/main/serge-steps.png) · [文章](https://huggingface.co/blog/huggingface/anatomy-of-a-bug-fixing-agent)。*

### 2. 生成补丁和验证补丁是两道检查

模型在本地检出中多轮修改，使用ruff、ty、transformers-mlinter等工具并再次查询历史决策。每个任务在短生命周期pod中运行，pod没有GitHub凭据或集群API令牌；系统只允许推送serge/分支和打开PR，最终合并由维护者决定。这些是作者描述的设计，本文未审计其实现。

验证阶段对未修改与已修改的代码各跑5次目标测试。仅修改期望值的补丁要额外审查：重复通过仍不证明它修正了根本问题。运行器退出、补丁应用失败或GPU超时属于基础设施或验证失败，不能算补丁好坏的证据；GPU超时可保留分支供人工查看，但不自动提PR。

### 3. 一个测试期望本来就错的案例

PVT v2测试连续七个夜间运行失败，原因是沿用了PVT v1的输出形状。作者描述Serge把期望从三维改为该模型的四维特征图，并调整切片与预期值，修改前后各5次验证后获准合并。模型工作用了36轮、56秒LLM时间，端到端约28分钟，说明主要价值之一是减少异步调度中的人工反复介入。这是原文案例，不是本次运行复现。

### 4. 看清哪些运行真正变成可审阅PR

约80天累计29项修复合并是长期结果；最近两周的117组失败是另一个窗口。86个实际模型会话中，28个没有安全补丁、18个补丁未通过GPU验证、5个验证超时、11个会话中途失败，只有24次产生验证通过的PR事件。重复事件去重后是19个PR，不能把24除以86称为合并率。

![Serge两周运行漏斗](../../../98-附件/原文配图/serge-funnel.png)

*图2：作者最近两周的漏斗：117组调度，29组无需进入推理，2组首请求失败，86组实际会话；24次验证PR事件去重为19个PR，其中16个在窗口内新建。图示截至统计时6个已合并、13个尚未合并，不同于约80天累计29项修复。 [原图](https://huggingface.co/datasets/huggingface/tarek-blog-posts-images/resolve/main/serge-funnel.png) · [文章](https://huggingface.co/blog/huggingface/anatomy-of-a-bug-fixing-agent)。*

原文报告这86个会话推理费约250美元，估算每个不同PR约14美元、每个合并PR约43美元；这只统计推理，未给GPU与人工审核的总成本。累计29项修复节省约43小时人工注意力也是作者估计，不能当作对照实验测得的收益。

## 适用条件与局限

- 适用于可稳定复现、可执行验证的维护任务；不代表任意仓库缺陷都能自动修复。
- 目标测试反复通过不是全库无回归的保证，尤其需要人工判断期望值更新是否合理。
- 运行数量、合并状态和费用属于作者统计窗口；未实时核对全部PR，不能当作当前合并总数。
- 两张正文技术图片均已读并保存；正文无视频、iframe或数据表，头像与页面图标不算配图。
- 没有运行Serge、下载模型或执行文章中的操作；不将模型替换的初步比较外推为普遍模型排名。

## 怎样理解与应用（AI 解读）

可把自动修复的产出分成“稳定复现”“有候选补丁”“通过验证”“进入审核”“已合并”，让每一步有独立证据。比如GPU超时应回到待验证，而不是给补丁贴成功或失败标签；若只改断言，应把原规格和参考输出交给审阅者。这是流程设计建议，未在本库执行实验。
