# 怎样确认 Agent 已从故障中恢复

## 摘要

Golda Manuel 提出按“从失败到恢复进展的一段过程”评估 Agent，重试本身不算恢复。恢复率以具备工具、权限和预算等恢复条件的失败过程为分母，以测试通过、产物有效或目标状态达成等证据确认成功；结束时仍未解决的合条件过程也要保留。作者用假设对照说明，恢复率较高的产品仍可能故障更多、最终任务成功更少，因此还应记录故障频率，以及所有合条件过程中的额外工具调用、耗时和 token 开销。这是一套评估方法与示例，文中没有真实产品的对照实测。

## 重点图文解读

### 从恢复进展的证据划定过程

一次故障及其后续调查、修改和重试构成同一个过程。执行成功的辅助动作不一定解除阻塞；应检查原操作是否成功，或另一条有效路径是否达到相同目标。

图示：故障发生、调查、重试、修复与验证

示例从缺少配置导致命令失败开始。读到文档和再次重试都没有结束同一次故障；补齐配置只是候选修复，直到原命令成功才确认恢复。图示是评估流程示例，不是真实产品的运行记录。 [原图](https://cdn-uploads.huggingface.co/production/uploads/6a10aac4480cf8331c3439b6/C_aIWHKBEkZc39psE5c5K.png) · [文章出处](https://huggingface.co/blog/phranzia/measuring-agent-recovery)

### 先定义分母，再比较恢复率

恢复率为“已验证恢复的过程数／具备恢复条件的失败过程数”。资格取决于评估中的工具、权限、预算与可用人工帮助，不按最终是否恢复筛选；到运行结束仍未解决的合条件案例也留在分母中。测试重新通过、产物存在且有效、状态满足目标，均可提供验证证据。

### 把开销与最终任务结果放在一起

工具调用、重试、token 和时间开销应覆盖所有合条件失败过程，包括没能恢复的案例。原文假设两个产品各执行100项任务：A有10次合条件故障、恢复7次，B有40次、恢复32次；B恢复率80%虽高于A的70%，最终成功任务却是90项对95项。这个反例说明恢复率不能代替总体可靠性，并非真实产品排名。

## 适用条件与局限

这是一套评估口径，没有真实产品的对照结果，也没有统一的自动判定器。比较时需保持失败资格和成功验证标准一致，区分可预期的失败操作与真正阻塞任务的故障。两张正文图片均已查看，仅保留有步骤含义的流程图；另一张为无坐标和数据说明的装饰图。假设对照表已读并节选关键数字；未发现正文视频、iframe或canvas。外链评估文档和论文未展开精读，未执行代码。

## 怎样理解与应用（AI 解读）

可以给同一故障的相关尝试分配同一个记录标识，保存阻塞原因、可用权限、额外开销与恢复证据。这样能发现“重试频繁却没有进展”的路径，也避免把一次故障中的多个动作重复计成多个恢复成功。
