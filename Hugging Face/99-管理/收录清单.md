Tarek Ziadé 介绍的 relore 将 GitHub 讨论历史与当前代码连接起来，保留发言者身份，区分维护者决定与贡献者判断，默认排除机器生成内容。在 Transformers 的一次排错中，Agent 通过历史符号搜索找到已有修复，避免重复补丁，并据维护者意见转向同类回归排查；这一经历随后催生了查询在途修复的 inflight 命令。查询在本地完成，更新索引需访问 GitHub。这是团队案例而非系统基准；一次测试中 Agent 自述，defs 提供更好的文件概览，所用 token 约为通读文件的5%。

### [把 Agent 会话变成可追溯记忆](../01-%E6%96%87%E7%AB%A0/%E5%B7%A5%E7%A8%8B%E4%B8%8EAgent/%E8%AE%B0%E5%BF%86%E4%B8%8E%E4%B8%8A%E4%B8%8B%E6%96%87/2026-09-03%20-%20%E6%8A%8A%20Agent%20%E4%BC%9A%E8%AF%9D%E5%8F%98%E6%88%90%E5%8F%AF%E8%BF%BD%E6%BA%AF%E8%AE%B0%E5%BF%86.md)

2026-09-03 · [原文](https://huggingface.co/blog/funes)

Funes 把多种编程 Agent 的会话统一为本地可检索记忆，结合向量与关键词检索返回原始片段、出处及上下文，避免只留下压缩结论。用户可选择把记忆同步到自己拥有、默认私有的 Hugging Face 数据集，以便跨机器使用。作者在两项依赖旧会话信息的任务中报告，检索方式每次成功任务的加权 token 成本分别约为书面交接的八分之一和四分之一，已计入一次性准备开销。这只是两个任务的结果，不能当作普遍节省比例；本地检索与远程同步也是不同的使用方式。

**要点：** 会话先统一为轮次与内容块，再分块建索引；检索返回原始对话并允许展开上下文，减少只保存浓缩结论造成的信息丢失。

### [BF16 微调中预期更新与实际写入为何不同](../01-%E6%96%87%E7%AB%A0/%E6%A8%A1%E5%9E%8B%E8%AE%AD%E7%BB%83/%E4%BB%BB%E5%8A%A1%E5%BE%AE%E8%B0%83/2026-09-06%20-%20BF16%20%E5%BE%AE%E8%B0%83%E4%B8%AD%E9%A2%84%E6%9C%9F%E6%9B%B4%E6%96%B0%E4%B8%8E%E5%AE%9E%E9%99%85%E5%86%99%E5%85%A5%E4%B8%BA%E4%BD%95%E4%B8%8D%E5%90%8C.md)

2026-09-06 · [原文](https://huggingface.co/blog/juiceb0xc0de/intended-and-realized-updates-in-bf16-fine-tuning)

社区作者用一个 1.87 亿参数 Mamba-3 模型在 GSM8K 上微调，发现 BF16 权重舍入会吞掉小更新，但约 4/3 的过冲比例并不是通用规律。在学习率 2e-4、3,000 步和 5 个种子的对照中，前向与反向计算仍使用 BF16，保持 FP32 优化器动量状态不变，改用 FP32 主权重反而让留出集每 token 损失增加 0.1220 nats。较低学习率的探索出现相反排序，但同时改变了权重和优化器状态精度，不能单独归因于权重存储。结果说明，写入更精确不必然在固定训练设置下学得更好；这一个人实验不能推广为 BF16 普遍优于 FP32。

**要点：** 更换参数存储精度时，应同时重做学习率扫描，并记录实际参数变化与留出损失。只看梯度非零，无法确认知识已写入权重。

Hugging Face 为 Transformers 接入 ggml 的 Metal 算子，并减少生成循环中的同步等待，使 Python/PyTorch 能直接运行压缩存储的 GGUF 权重。作者在32GB内存的 M2 Max 上测试三个 Qwen 检查点，报告速度接近 llama.cpp；但 Transformers 含预填充、取预热后三次运行的最好值，llama-bench只测解码并取三次平均，不能视为同条件胜负。发布时需 Transformers 主分支及兼容的 PyTorch、kernels，压缩权重路径仅支持 Apple Silicon 的 MPS 与 Qwen3.5架构（含兼容Qwen3.8），优化面向单个交互会话，带填充的批处理尚不能享受全部优化。缺少兼容量化算子会解量化并增加内存占用。
