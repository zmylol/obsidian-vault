# 跨 Claude 产品的隔离与安全边界

## 摘要

Anthropic 总结了 claude.ai、Claude Code 和 Cowork 的隔离设计，核心是限制智能体出错后能够触及的资源。三者的代码执行分别采用云端临时容器、本地系统沙箱和本地虚拟机，适应不同任务与用户监督能力。真实漏洞复盘显示，成熟隔离组件之外的自建代理和信任判断也会失守：获准访问的域名仍可能把文件送入攻击者账户，因此需要校验会话身份与具体权限。隔离应与模型防护叠加，且不能保证已挂载的工作资料不会受损。

## 重点图文解读

### 风险同时取决于概率和影响范围

环境限制约束模型能够触及什么；模型防护只影响它倾向于做什么。两者需要叠加。

图示：风险收益示意图将伤害概率、影响范围与收益放在天平两侧，比较限制风险、拒绝部署和高效用三种情形；它是概念图，不是量化安全评分。

### 隔离方式匹配工作场景

claude.ai 的代码执行使用临时云端容器；Claude Code 结合本地系统沙箱与审批；Cowork 的代码执行使用本地虚拟机。Cowork 后来把运行循环和本地 MCP 服务器移到虚拟机外；虚拟机仍会挂载选定工作目录及 .claude，因此不能把整个产品的所有操作都视为被虚拟机隔离。 [原文 Pattern 3](https://www.anthropic.com/engineering/how-we-contain-claude)

### 允许域名还不够

一次泄漏通过获准访问的服务进入攻击者账户。修复增加会话身份校验，说明网络放行还应限制调用所代表的权限。

## 适用条件与局限

这些是特定产品的工程经验。VM 也会降低主机安全软件的可见性；隔离并不保证已挂载资料不会受损。

## 怎样理解与应用（AI 解读）

为本地 Agent 建边界时，列出目录、联网目的地及账户权限，比只写“谨慎操作”更可验证。用一份无敏感数据的测试目录检查实际可达范围。
