## 摘要

Anthropic 研究者让 16 个 Opus 4.6 智能体协作开发 Rust 实现的 C 编译器，两周内经过近 2,000 次会话、花费约 2 万美元，得到约 10 万行代码并能构建 Linux 6.9。推进工作的关键是持续测试、共享任务记录，以及借助 GCC 对照拆分内核编译故障。它仍需 GCC 完成 x86 的 16 位启动部分，演示也借用了外部汇编器和链接器，生成代码的效率较差。这是能力边界实验，尚不能替代成熟编译器。

## 正文要点与配图

## 无限循环如何维持进度
作者让 Agent 把大目标拆成小任务、记录工作状态并在完成后立即领取下一项，以避免单次交互结束就等待人类。每个实例在容器中运行，多个实例共享仓库但分担实现、测试和文档等角色。

## 测试是协调机制
自动测试和持续集成把并行修改拉回共同质量标准；没有这些反馈，更多 Agent 只会增加冲突和无法定位的错误。编译器产物说明规模可能扩大，但不代表代码质量达到生产要求。

这里的并行能力依赖任务分解：作者用 GCC 编译多数内核文件、让新编译器处理剩余文件，以对照测试定位可分别修复的错误。产物仍需 GCC 完成 x86 的 16 位启动部分；演示使用外部汇编器与链接器，生成代码效率低于成熟编译器，不能据“能构建 Linux”推定已经可替代它们。 [原文 Evaluation 与 Make parallelism easy](https://www.anthropic.com/engineering/building-c-compiler)

## 适用边界
运行无限循环必须在容器和受控预算中，不能直接在真实机器执行；文章是一次压力测试与工程经验，不是通用成功保证。
