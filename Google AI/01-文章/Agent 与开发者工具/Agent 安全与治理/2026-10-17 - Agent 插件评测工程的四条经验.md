## 摘要

Google Cloud 总结构建 Developer plugin 时的四条评测经验：评分应读取真实工具调用轨迹而非只看最终摘要；遥测必须保留并发调用的 turn 结构；live run 与 plan-only run 要并列测试；用人工整理的 golden set 作为持续回归基线。文中 11 个提示的初始套件曾把三个实际通过的任务判为失败，原因是最终文字没有复述已执行的检查。文章是作者的工程案例，不等于所有 Agent 框架都适用，本次未运行插件或复现实验。

## 重点文字解读

### 评分对象应是执行轨迹

作者回顾了 Google Cloud Developer plugin 的 11 个提示评测：最终摘要把 3 个实际通过任务判为失败，因为摘要没有复述已执行的命令检查。原始工具调用和 transcript 才能说明系统真正做了什么。

图示：Agent 轨迹评测中，最终摘要与真实工具执行可能出现不一致。

*图：原文用 Cloud Run 清理任务说明只看总结的误判；应检查命令、顺序和验证过程。原图：[Google Cloud](https://storage.googleapis.com/gweb-cloudblog-publish/images/Image_1_XmJ1pt2.max-1300x1300.png)。*

### 保留并发 turn 与两种运行条件

遥测提取不能把并发工具调用压扁成单一时间线，否则会丢掉技能注入与调用时序。live run 检查真实执行和安全克制；plan-only run 去掉凭据，暴露模型的路由与治理盲点。

### Golden set 作为持续基线

基线要覆盖 harness、模型和工具的组合行为；模型和插件会变，但同一组人工整理的理想轨迹能支持持续回归。

## 适用条件与局限

- 这是一个 Google Cloud Developer plugin 的工程案例，11 个提示和具体失败模式不能直接代表所有 Agent 系统。
- 本次未运行插件、读取真实遥测或复现实验；文章中的平台和插件能力需按当前文档核对。

## 怎样理解与应用（AI 解读）

评测时把最终答案、工具调用顺序、权限边界、计划与实际差异分别打分；保留 live 与 dry run 的对照，尤其检查自动化流程是否在权限错误下掩盖了推理或治理缺陷。
