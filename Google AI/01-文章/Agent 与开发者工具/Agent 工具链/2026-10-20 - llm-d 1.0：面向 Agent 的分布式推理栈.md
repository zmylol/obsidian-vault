# llm-d 1.0：面向 Agent 的分布式推理栈

## 摘要

Google 与 Red Hat、IBM 等社区发布 Kubernetes 原生的 llm-d 1.0，面向多步 Agent 的长前缀和突发负载，组合缓存路由、分层 KV cache、prefill/decode 解耦与 TPU/GPU 集群。会议演示 1,000 个沙箱 Agent 共用端点；官方称 Ironwood TPU 编程负载的 TTFT 中位数降低超过 85%、吞吐提高 2.4 倍。数字依赖指定硬件与基准，本文未复测。

## 重点图文解读

### 从通用负载均衡转向上下文感知

llm-d 1.0 把 vLLM、SGLang、Kubernetes 和 Google Cloud TPU/GPU 组合为一个可编排的推理池。文章针对 Agent 多轮调用、共享长前缀和突发流量，强调缓存感知路由、分层 KV cache 与优先级流控，让同一会话尽量回到持有其上下文的副本。

### 1.0 能力与实测口径

1.0 提供 v1 API、路由高可用、零停机更新、会话感知调度和 Responses API 状态；同时保留 prefix/load-aware routing、KV cache offload、prefill/decode 分离、专家并行和批推理。文章在 PyTorch Conference 演示 1,000 个沙箱 Agent 访问单一端点；这属于演示规模，不是所有部署的容量保证。

![llm-d 多节点编排与 TorchTPU 单节点模型引擎在 GKE/TPU 上的组合。](../../../98-%E9%99%84%E4%BB%B6/%E5%8E%9F%E6%96%87%E9%85%8D%E5%9B%BE/llm-d-torch-tpu-stack.png)

*图：原文展示 Kubernetes 编排层与 TorchTPU 引擎的关系。* [原图](https://storage.googleapis.com/gweb-cloudblog-publish/images/2_-_Figure_2_-_llm-d_1.0_and_TorchTPU_stac.max-2200x2200.png) · [原文](https://cloud.google.com/blog/topics/ai-infrastructure/llm-d-1-0-an-open-source-stack-for-distributed-inference/)

### 延迟、吞吐与时分片

原文称在 Ironwood TPU（TPU 7x）Agent 编程负载中，前缀路由与主机内存卸载让 TTFT 中位数比普通 Kubernetes Service 降低超过 85%，吞吐提高 2.4 倍；RL 训练中，TPU/GPU 时分片把聚合加速器 duty cycle 从约 40% 提高到 70% 以上。文中还给出异步处理器，可从 Pub/Sub 或 Redis 队列接入对延迟不敏感的任务。

## 适用条件与局限

- 数字来自指定硬件、路由配置、工作负载和公开基准；不能直接外推到其他模型、集群或请求分布。
- llm-d 由社区协作并依赖 Kubernetes、vLLM、SGLang 等组件；运行所需的运维、硬件和观测成本未在本文完整量化。
- 本次未部署集群、运行基准或精读外链 GitHub/llm-d 文档。

## 怎样理解与应用（AI 解读）

评估 Agent 推理平台时，应固定模型、上下文长度、并发轨迹和 SLO，分别测 TTFT、端到端延迟、吞吐、KV cache 命中和成本。把缓存感知路由与时分片逐项做开关对照，才能判断收益来自哪一层，并检查后台 RL 或批任务是否挤占交互请求。
